# Database and cloud storage (Supabase)

The app works in two storage modes, chosen automatically:

| Mode | When | Where data lives |
|---|---|---|
| **On this device** | Supabase not configured, or no parent signed in | Browser `localStorage` (not backed up or synced) |
| **Cloud** | `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` are set **and** a parent is signed in (Grown-ups → Account) | Supabase Postgres, protected by Row Level Security |

A child never needs an account: playing works signed-out. The parent account is just an email and password.
Switching: signing in uses the cloud; signing out returns to the device copy (nothing is deleted either way).
Grown-ups → Account → *Copy device data to cloud* does a one-way import of real (non-demo) profiles and history.

**Code:** `lib/database/supabase-repository.ts` (implements the same `Repository` interface as `local-repository.ts`),
`supabase-mapping.ts` (row ⇄ app types), `supabase-client.ts` (public key only). After every change the repository re-reads from the
database. Which child is "active" is a per-device choice kept in the browser.

**Auth setup note:** by default Supabase may require new parents to confirm their email before signing in (Supabase dashboard →
Authentication → Providers/Sign In). The app tells the parent to check their email. Default email sending is rate-limited, so for a
single-family app you can either keep confirmation on, or create your account in the dashboard (Authentication → Users → Add user).

## Files
- `supabase/migrations/0001_init.sql` — tables, constraints, indexes
- `supabase/migrations/0002_rls.sql` — Row Level Security, privileges, `export_child_data()` and `delete_child_profile()`
- `supabase/migrations/0003_least_privilege.sql` — resets table privileges to the minimum (see below)
- `supabase/seed.sql` — generated curriculum + activities (`npm run db:seed-sql`); safe to re-run

## Tables
Shared content (read-only to signed-in users): `learning_domains`, `curriculum_frameworks`, `learning_objectives`,
`objective_prerequisites`, `objective_framework_mappings`, `activities`, `activity_objectives`.
Private family data (RLS: a parent sees only their own): `child_profiles`, `activity_attempts`, `learning_progress`,
`parent_settings`, `parent_activity_overrides`.

## Changes from the original brief, and why
- Text ids (`MATH-CNT-01`, `count-the-apples`) instead of uuids, so git content and rows share one identifier.
- `objective_prerequisites` join table instead of an array, so foreign keys enforce it.
- `activities` gained `world`, `review_status`; a CHECK forbids *published but unreviewed*.
- `activity_attempts` gained `duration_seconds`, `rounds` (per-round evidence, never transcripts) and `parent_note`.
- `parent_activity_overrides` stores each parent's publish/retire/review choices.
- `child_profiles` has **no** date of birth, photo, school or address; nickname ≤ 24 characters.
- Deletion rules: deleting a parent or profile cascades to their private rows; activities/objectives that have attempts cannot be deleted (retire them).

## Least privilege (migration 0003): a real finding
Supabase automatically grants broad privileges (including `TRUNCATE`, which RLS does not control) on every new table to `anon` and
`authenticated`. 0002 only *added* grants, so signed-in parents kept more rights than needed (RLS still stopped reading other
families' rows and editing shared content). 0003 revokes everything and grants only: `SELECT` on shared content; `SELECT/INSERT/UPDATE/DELETE`
on family tables; nothing for `anon`. The local test now reproduces Supabase's default grants, and fails without 0003.

## What was tested
`tests/integration/database-rls.test.ts` runs both migrations and the seed in **PGlite** (Postgres 18 compiled to WASM) with a stand-in for
Supabase's `auth` schema and verifies: parents see only their own rows; cannot update, delete or write onto another parent's child;
cannot give a profile away; anonymous users are denied everywhere; curriculum is read-only; export/delete only affect the caller;
cascade deletion; constraints; least-privilege grants. The same behaviours were checked on the **live** project schema with SQL acting as signed-in parents (rolled back, no data left).
**Not tested:** the live HTTP API (PostgREST), Auth (sign-up/sign-in/email confirmation) or the browser flow, because the build sandbox's network policy blocked `supabase.co`. The adapter itself is tested against an in-memory stand-in (`tests/fake-supabase.ts`), which checks our logic, not Supabase.

## Setting up another project
1. Create a Supabase project. 2. `supabase link --project-ref <ref>` then `supabase db push` (applies 0001–0003), or run the three migration files in the SQL editor in order.
3. Run `supabase/seed.sql` (generated by `npm run db:seed-sql`; safe to re-run). 4. Put the project URL and publishable key in `.env.local` (and Vercel env vars).
Never put the service-role key in the browser or in `NEXT_PUBLIC_` variables.

## Local storage limits (on-device mode)
Data lives in one browser on one device; it is not backed up or synced; clearing site data or private browsing erases it. Use
Grown-ups → Data & privacy → Download export for a copy, or sign in and import to the cloud.
